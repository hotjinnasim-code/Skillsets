**Concrete findings and proposed changes**

1. **The importable API's workspace boundary is captured too early.** [Helper line 21](</Users/nahyeonbin/Desktop/_Codex/Ducttape Poster/drafts/layout-guide-helper/revision-v2/make_layout_guide.py:21>) assigns `ROOT = Path.cwd().resolve()` once, at import. `bounded()` uses that value at lines 85–92; project-font permission also includes that captured root at lines 22–32 and 239–241. In contrast, [README line 29](</Users/nahyeonbin/Desktop/_Codex/Ducttape Poster/drafts/layout-guide-helper/revision-v2/README.md:29>) describes paths relative to the calling process's current workspace. A process that imports the module in directory A, then enters task workspace B before calling `render()`, still admits A and rejects B; explicit project fonts in B are likewise rejected. It can therefore create outputs in the old directory instead of honoring the documented current task boundary. This is a static, deterministic mismatch, not a claim that the normal CLI fails.

   **Proposed change:** capture the resolved workspace once at the start of each `render()` call and pass it through input/output validation, relative-path resolution, input-relative manifest paths, and project-font checks. Keep the installed helper's location independent of that boundary. Do not change a module global around the call, which would introduce interference between callers. If the API deliberately remains import-bound, narrow its README contract explicitly and require import after entering the task workspace; the current contract must not remain ambiguous. The existing separate-workspace test exercises a fresh CLI process, so it does not cover the import-then-change-directory API behavior.

2. **Candidate U describes the technique but does not wire the supplied helper into an executable bundle.** [Production brief line 43](</Users/nahyeonbin/Desktop/_Codex/Ducttape Poster/drafts/candidate-u/references/production-brief.md:43>) reaches [layout-guide.md](</Users/nahyeonbin/Desktop/_Codex/Ducttape Poster/drafts/candidate-u/references/layout-guide.md:3>), but that reference never names `make_layout_guide.py`, its JSON contract, its README, or a workspace invocation. The helper README's example uses a placeholder `/path/to/skill/scripts/make_layout_guide.py`. Read-only existence checks found neither `candidate-u/scripts/make_layout_guide.py` nor `candidate-u/scripts/README.md`. Thus the supplied candidate is a prose integration draft; its text alone does not give a producer a runnable route to this particular helper. This finding is about the supplied tree, not an inventory of any installed skill elsewhere.

   **Proposed change:** when bundling this helper in a future revision, give it one stable skill-relative location and add a short optional link to its local contract plus a single CLI recipe. Resolve the script from the skill location while running Python with the task workspace as cwd; do not `cd` into the installed skill directory. Use an already available compatible Python/Pillow runtime and explicit existing fonts; if either is unusable, skip the guide and continue with the positive native production brief. This needs no setup wizard, credentials, installation step, reference search, stock layout/example menu, or per-request plan file requirement. This review does not perform the proposed bundling.

3. **The missing-glyph guarantee is stronger than the cmap check.** [Helper line 173](</Users/nahyeonbin/Desktop/_Codex/Ducttape Poster/drafts/layout-guide-helper/revision-v2/make_layout_guide.py:173>) collects all eligible Unicode format-4/12 subtables. Its `has_glyph()` returns true when *any* of those subtables maps a character to a nonzero glyph (lines 197–228). Pillow loads the face separately at line 258, and the code never ties coverage to the cmap that FreeType actually selects. If eligible subtables disagree and the active one lacks a character covered by another, the missing-character check at lines 352–354 can accept it even though the raster text uses a missing glyph. [README line 86](</Users/nahyeonbin/Desktop/_Codex/Ducttape Poster/drafts/layout-guide-helper/revision-v2/README.md:86>) currently promises failure rather than replacement glyphs. This is an uncovered static logic gap; no discrepant installed font was tested and no raster was generated during this review.

   **Proposed change:** make coverage agree with the face's effective cmap. A small conservative alternative is to reject inconsistent requested-character coverage across eligible subtables with a clear unsupported-font error and let the caller skip the optional guide. Keep the existing shaping caveat and prohibition on implicit font fallback. Do not solve this by downloading fonts, silently substituting them, or changing client copy. The inspected tests use one Apple TTC for successful font rendering and do not address disagreeing cmap coverage.
